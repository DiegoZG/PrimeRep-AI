# Workout reliability diagnostics (client)

Collection is default off through the independent `workout_reliability_monitoring_enabled` flag. It does not require purchases, enforcement, onboarding gating or paid access. Enable selected synthetic preview accounts first. The authenticated `/v1/feature-flags` response is polled on foreground entry and at most once per minute while active. Missing legacy fields mean off. A received disabled snapshot stops capture and delivery; an already-issued request can finish, and the server independently applies its current effective flag.

`WorkoutDiagnosticsSync` owns one account/environment collector outside SubscriptionContext. The runtime captures account generation, including account A→B→A, and keeps the same actor during normal token refresh so an in-flight workout acknowledgment remains observable. Credentials are read from the current owned token reference. Diagnostic HTTP uses direct fetch with a five-second deadline/abort, deliberately avoiding `httpClient` subscription side effects. It never refreshes tokens, logs out, opens a paywall, or calls workout mutations. A diagnostic 401/403 suspends sending until normal authentication supplies a new token. Transport failures retry only in foreground, from five seconds up to a sixty-second cap. Flag checks also stop on auth failure until normal credential replacement. No OS background task is introduced.

## Capture and persistence

`workoutDiagnosticsBridge.ts` is a pure, inert observer bridge. Importing native/web workout stores does not initialize diagnostic storage, networking, native SDKs or timers. Inactive request observation returns the original service promise. Active callbacks are fenced to their original account generation and environment. Observer exceptions cannot escape into logging. Stores project only operation ID/type into the local observer; no business payload is passed to it. Operation IDs are used only as local sidecar lookup keys and are never sent in events.

The client stores a versioned, account/environment/API-scoped AsyncStorage sidecar, separate from SQLite and web workout snapshots. It maps existing operation IDs to independent diagnostic UUIDs and immutable first-enqueue observation times. This intentionally replaces the plan's optional business-store columns: a missing/broken diagnostic store cannot prevent workout database initialization, save or replay. No API, business payload, idempotency key, fingerprint, retry policy, target or rest deadline changes.

For newly observed durable operations, timing starts when the existing save/enqueue function is entered, before its queued durable write, and is retained only after that write succeeds. Live durations use the monotonic clock around that existing local path, including its queue/read/validation/storage work; they are not isolated SQLite transaction times. Local success requires an actual successful write and a positive saved-set count. Validation, admission conflict, storage and unknown local failures remain distinct. A no-op is not reported as a successful write.

Legacy operations observed without prior metadata receive a stable trace with unknown original enqueue age. SQL `created_at` and workout dates are never used to synthesize age; missing age is never zero. Active mappings survive rewrites, retry, token refresh, app upgrades and JS runtime restart while within the metadata bound. Successful acknowledgment is observed only after the existing canonical merge is durably saved. Canonical GET reconciliation emits a reconciled terminal outcome and no synthetic write-attempt event. An attempted write that fails remains nonterminal. Explicit order supersession and cancelled finish/conflict intents remain separate outcomes. Finish HTTP results and terminal local cleanup results are separate stages; cleanup is an attempted local cleanup, not independent proof of server completion.

The recovery marker compares the trace's initial JS runtime identifier with the current identifier. Token/actor rebinding in the same JS runtime is not a restart; a new JS runtime (including a developer reload) is. Invalid/negative/over-one-year wall-clock ages and unavailable/invalid/over-one-day monotonic durations are omitted. Event observation times remain client clocks; server receipt time controls server retention and report buckets.

## Bounded diagnostic storage and delivery

The sidecar's total JSON is bounded to 128 KiB, with at most 200 buffered events and 512 trace mappings. Events expire seven days after local capture; invalid-clock/future buffers are discarded. Oldest buffered events are evicted first on count/byte overflow. Terminal mappings expire seven days after retirement. Active mappings are kept within the count/byte bounds; oldest metadata eviction can lose trace/age coverage for a very large backlog, which later becomes an unmatched legacy/unknown-age observation. It never removes a workout operation. Startup capture while a diagnostic read stalls is independently capped at 200 projected signals and 128 KiB; excess signals are discarded with a bounded collection-gap count. A dropped startup signal counts one missing observation, which may have contained multiple operation projections; it is not a count of lost workout operations.

Capture changes memory immediately and coalesces asynchronous diagnostic writes. One diagnostic write per key runs at a time; shared per-key read/write fencing prevents an older actor's delayed write from overwriting a new actor's state during token/account rebinding. Failed writes wait thirty seconds before another storage attempt. Slow diagnostic storage never joins the business write queue. Unchanged idle ticks do not rewrite the sidecar. Queue gauges use the latest observed queue, coalesced at a fifteen-second minimum interval; renders/rest ticks do not each produce events.

Delivery is one flight per owned runtime, in compatible batches of at most twenty events and 32 KiB. Already-buffered envelopes retain the platform/release that originally observed each event, including after an app upgrade. New observations use the current capture build, even for an older operation trace. Event UUIDs survive retry; the server deduplicates events and logical terminal outcomes. A valid receipt must account for the whole sent batch. A flag-off receipt retires that batch, keeps other buffered diagnostics, and suspends sending until a later enabled snapshot. An invalid receipt or diagnostic network/server/rate-limit failure changes only telemetry delivery. Only fixed event fields pass schema validation; restored sidecars/envelopes are projected before reserialization.

These are best-effort observations. A crash before the independent sidecar write, corruption, overflow, stalled initialization, ownership transitions, invalid clocks, disabled collection or expiry can leave missing enqueue/request/result/terminal coverage. The collection-gap event is itself bounded best-effort telemetry; it cannot count every lost observation. Status-less `HttpError` transport-wrapper failures are grouped under `network`, which includes transport/response-processing failures and does not prove the device was offline. No user training values, exercise identities/names, notes, feedback, dates, tokens, email addresses, payloads, URLs or raw exception messages enter event JSON. The app makes no 99.9% reliability or zero-data-loss claim from these samples.

Automated suites cover both store implementations, mounted player logging/navigation with stalled/throwing diagnostics, durable saves and failures, actual writes versus reconciliation, retry/nonterminal failure, finish stages, restart/legacy clocks, upgrades, corruption/privacy, count/byte overflow, stalled startup reads, same-key delayed writes, account/environment ABA, token refresh, rollback, foreground behavior, auth suspension and idle-write bounds.
